Add a `materialized_table` materialization built on Flink's `CREATE OR ALTER MATERIALIZED TABLE ... AS SELECT`. It is declarative: every run re-asserts the definition and lets Flink reconcile it — a new table is created, any change (columns, `WITH` options, or query logic) is evolved in place, and an unchanged definition is a server-side no-op. `--full-refresh` drops (`DROP MATERIALIZED TABLE IF EXISTS`) and recreates, which is also how you change `distributed_by` (fixed at creation) — note the drop permanently deletes the backing Kafka topic and its data. Supports `config(distributed_by={...}, with={...}, start_mode=...)`, with all eight documented `start_mode` forms; `freshness_interval`, `refresh_mode`, and `partition_by` are rejected with a compile error. Switching a model that already exists as a regular table/view to `materialized_table` is guarded: a plain run fails with guidance, `--full-refresh` performs the switch. A re-run within Flink's brief establishment window is transiently rejected (`being modified`) and retried automatically. See MATERIALIZATIONS.md.
