Add a `materialized_table` materialization built on Flink's `CREATE OR ALTER MATERIALIZED TABLE ... AS SELECT`. It is declarative: every run re-asserts the definition and lets Flink reconcile it — a new table is created, any change (columns, `WITH` options, or query logic) is evolved in place, and an unchanged definition is a server-side no-op. Note that evolving a *stateful* model (aggregations, joins, windows) silently resets its results — Flink discards processing state and resumes from current offsets without reprocessing history — so definition changes to stateful models should run with `--full-refresh` (see MATERIALIZATIONS.md). `--full-refresh` drops (`DROP MATERIALIZED TABLE IF EXISTS`) and recreates, which is also how you change `distributed_by` (fixed at creation) — note the drop permanently deletes the backing Kafka topic and its data. Supports `config(distributed_by={...}, with={...}, start_mode=...)`, with all eight documented `start_mode` forms; `freshness_interval`, `refresh_mode`, and `partition_by` are rejected with a compile error. Switching materializations is guarded in both directions: a model that already exists as a regular table/view can't become a `materialized_table` on a plain run (and vice versa — the drift check detects a leftover materialized table under a regular model's name instead of silently skipping); in both cases the run fails with guidance and `--full-refresh` performs the switch. A re-run within Flink's brief establishment window is transiently rejected (`being modified`) and retried automatically. See MATERIALIZATIONS.md.
