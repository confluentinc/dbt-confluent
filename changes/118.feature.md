The schema drift check for `table` and `streaming_table` models now compares a Flink `sql.dry-run` of the model's SELECT with a dry-run of `SELECT * FROM` the existing table, instead of creating and introspecting a temporary table, so a re-run no longer creates (and later drops) a `__dbt_tmp_schema_check_<model>` table per model. Column types are compared as Flink reports them, ignoring top-level nullability as before, and comparing the model's `CHAR` or `VARCHAR` MAP keys and `MULTISET` elements as the `VARCHAR(2147483647) NOT NULL` an Avro or JSON table stores, as the temporary table did (a Protobuf `streaming_table` still reports drift for these, as before); nullability inside composite types is compared, except at a string MAP key or `MULTISET` element on the model's side. The dry-runs evaluate the SELECT in the mode the model is built in (snapshot for `table`, `streaming_query` for `streaming_table`), which changes behavior in three cases: a `table` whose SELECT only works as a streaming query now fails the drift check (its `--full-refresh` already fails); a `table` whose SELECT only works as a snapshot query no longer fails it; and the profile's or model's `execution_mode` no longer affects the drift check for these models. The temporary table remains the fallback for `streaming_source` models and wherever a dry-run can't stand in for it (no result schema, or duplicate column names), and the dry-run path also reclaims a temp table leaked by an earlier run that died hard.
